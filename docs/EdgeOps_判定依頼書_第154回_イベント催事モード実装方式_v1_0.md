## 0. 依頼の要旨

イベント・催事モードの残タスクのうち、**実装方式が未確定の4件**について判定を求める。

| # | 実装単位 | 仕様書 | 判定を求める理由 |
|---|---|---|---|
| E5 | 承認権限（event＝管理者のみ） | 第9章 | **承認にRPCが存在せず、L3保護領域に触れる可能性** |
| E9 | 引き継ぎ非表示（サイネージ側） | 第13章 | **サイネージが業種を判定できずEF改修が必須と判明** |
| E3 | サイネージ枠1台制限 | 第7章 | 仕様書が案ア／イ／ウを未決のまま提示 |
| E6 | 写真投稿権限（event＝管理者のみ） | 第10章 | 第119回判定（is_creator限定の撤回）との整合 |

あわせて **E7（既読表示の粒度）・E10（期限切れ専用画面）** の解釈を確定したい。

**最優先制約（仕様書 第0章）**：実顧客（スマイルホテル様）が本番稼働中。**通常グループの既存挙動を一切変更しない。** すべての分岐は `industry='event'` に限定する。

## 1. 実コードで確認した事実（推測ではない）

判定の前提となる事実。すべて 2026/7/25 時点の本番コードを読んで確認した。

### 1-1. 承認処理にRPCは存在しない（E5の前提）

```js
// index.html L3373  approveMember()
await supabase.from('group_members')
  .update({ status: 'approved', approved_at: new Date().toISOString() })
  .eq('id', memberId);            // ← L3375・フロントからの直接UPDATE
```

仕様書 第9章は「処理側（approveMember 経由のRPC等）でも `is_creator=true` を確認して拒否する」としているが、**その処理側が存在しない。** 承認は `group_members` への直接UPDATEである。

### 1-2. サイネージは業種を判定できない（E9の前提）

| 箇所 | 事実 |
|---|---|
| `signage-fetch` L139 | `group_sessions` を `.select('*')` で取得（DBからは industry が取れている） |
| `signage-fetch` L276-287 | `safeGroup` は**明示的なホワイトリスト**。返すのは `id / group_id / group_name / facility_id / region / link_url / expires_at / created_at` の8項目のみ。**industry はレスポンスで捨てている** |
| `signage.html` 全2,338行 | **`industry` という文字列が1つも存在しない** |
| `signage.html` L617 / L1425 | 引き継ぎは `section-handover` ＋ `_globalSignageData.handover_notes` で描画 |
| `signage.html` L1597-1605 | `handoverItems.length > 0` が偽のとき、**セクションと区切り線を both `display:none` にする処理が既にある** |

→ **サイネージ側で event を判定する手段が現在ゼロ。** E9 は「判定不要・フロント表示制御のみ」では実現できない。

### 1-3. upload-image には認可ブロックが既にある（E6の前提）

```ts
// upload-image/index.ts L188-199  Step 4: 認可判定
// [第119回] 画像投稿の is_creator 限定を撤回。approved・非サイネージなら投稿可。
const { data: posterMember } = await supabase
  .from('group_members')
  .select('is_signage, status')       // ← is_creator は select していない
  .eq('eo_uid', eoUid)
  .eq('group_session_id', groupSessionId)
  .eq('status', 'approved')
  .maybeSingle();
```

service role クライアントで `group_members` を引いているため、**`is_creator` を select に足し、`group_sessions` から industry を引く追加クエリ1本で第10章の処理側制御は成立する。**

### 1-4. E1・E4 は判定不要で確定（参考）

```js
// index.html L1682-1691  createGroup()
p_expires_at: expiresAt.toISOString(),   // 現在は作成日＋1年
p_max_members: 50                        // ← ハードコード
```

event のとき「利用最終日の翌日00:00」と `202` に差し替えるだけで、RPC本体は不変更。仕様書 第4章・第8章の想定どおりであった。

**ただし付随修正が1件ある。** `joinGroup()` L1777 の GROUP_FULL メッセージが `'このグループは満員です（最大50名）'` とハードコードされており、event では誤表示になる。E4 の実装指示書に含める（判定不要と考える）。

### 1-5. 期限切れ処理の現状（E10の前提）

```js
// index.html L1513-1524  restoreSession() 内
if (currentGroup?.group_id?.startsWith('SL-') && currentGroup?.expires_at) {
  if (new Date(currentGroup.expires_at) <= new Date()) {
    clearEdgeOpsLocalStorage();
    document.getElementById('start-expiry-notice').style.display = 'block';
    showScreen('screen-start');   // ← 既に「作成／参加画面」へ誘導している
  }
}
```

**この処理は通常グループにも等しく効いている。** また `loadMyGroups()` L4227-4239 は `group_sessions` から `id / group_id / group_name` しか select しておらず、**`expires_at` も `industry` も取っていない。**

## 2. 論点1【E5】承認権限の処理側制御をどこに置くか ★最重要

**仕様書 第9章**：event では承認は管理者（`is_creator=true`）のみ。表示制御だけに頼らない。

現状は 1-1 のとおりフロントからの直接UPDATEであり、処理側制御を入れるには `group_members` に手を入れる必要がある。**`group_members` は L3保護領域である。**

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **案A** | フロント表示制御のみ（`screen-approval` 入口と承認ボタンを非表示）。処理側制御は入れない | L3不可触。当日中に完了。通常グループへの影響ゼロ | **仕様書 第9章「表示制御だけに頼らない」に反する。** 一般参加者がコンソールから直接UPDATEすれば承認できる |
| **案B** | `group_members` の UPDATE RLS Policy に event 条件を追加 | RPC新設が不要 | **L3のPolicy変更。通常グループの承認に影響が及ぶ危険。**Policy誤りで全承認が停止する |
| **案C** | 新規RPC `approve_member_safely` を追加し、`group_members` の UPDATE 権限を段階的に剥奪 | 確実。返信機能の段階A〜Dで実績のある無停止移行手順を再利用できる | 工数最大。DDL＋GRANT変更を伴い、8/6 目標に対して重い |

### 起案側の意見

**案Aを推す。** 理由は3点。

1. **脅威モデルが小さい。** 承認できるのは「そのグループの承認済みメンバー」だけであり、部外者ではない。誤承認が起きても仕様書 7-1 の割り切り（作り直す）で回収できる。
2. **event は使い捨て・短命。** 期限切れ後は復活しない（第15章）ため、恒久的な権限設計を急ぐ必要がない。
3. **通常グループのリスクがゼロ。** 案B・案Cはどちらも `group_members` に触るため、スマイルホテル様の承認フローを壊す可能性がある。第0章の最優先制約に照らして割に合わない。

**案Cを採る場合は 8/6 に間に合わない可能性が高い。** その場合は Plus版へ送ることを提案する。

## 3. 論点2【E9】サイネージ側の引き継ぎ非表示をどう実現するか

**仕様書 第13章**：event では引き継ぎ機能を表示しない。

1-2 のとおり、サイネージ側は業種を知る手段を持たない。仕様書 第13章の本文はスマホ側（`screen-handover`・第127回の復元対象）しか記述していないが、**サイネージにも引き継ぎセクションが存在する**ため、対応方針を確定したい。

| 案 | 内容 | 変更ファイル |
|---|---|---|
| **案X** | `signage-fetch` が `industry='event'` のとき `handover_notes` を空配列で返す | **signage-fetch のみ** |
| 案Y | `safeGroup` に `industry` を追加し、`signage.html` 側で非表示分岐 | signage-fetch ＋ signage.html |
| 案Z | サイネージは対象外とし、引き継ぎを表示したままにする | なし |

### 起案側の意見

**案Xを推す。** 理由は3点。

1. **`signage.html` を1行も触らずに済む。** 1-2 のとおり L1597-1605 が空配列を既に正しく処理している（セクションと区切り線を非表示）。7/6 の誤検知事故の当該ファイルであり、触らないことに価値がある。
2. **仕様書 21-10(3)**「signage.html は index.html の関数を流用せず自己完結」と整合する。
3. **案Zは第13章に反する。** イベントで引き継ぎを使わないと決めた以上、サイネージに残るのは不整合。

案Xの副作用として、**`industry` はサイネージ側に一切露出しない**（将来サイネージで event 固有の表示を足す場合は別途EF改修が必要）。この点を許容するかも含めて判定いただきたい。

## 4. 論点3【E3】サイネージ枠1台制限の実装方式

**仕様書 第7章**：主催者が1台目のサイネージ枠を早い者勝ちで確保する。予約はしない（7-1）。

`join_group_with_member` は不可侵RPCであり、現在「1グループ1台」の制御は存在しない（第7-2章）。

| 案 | 内容 |
|---|---|
| **案ア** | フロントチェック。参加前に `is_signage=true` の承認済み／申請中メンバーの有無を問い合わせ、いれば弾く |
| 案イ | 新規RPCを追加し、DBレベルで原子的に弾く |
| 案ウ | 案アの制御に加え、厳密な排他は求めず運用でカバー |

### ★実装前に確認が必要な事実（未確認）

**案ア・案ウは「まだ参加していないグループの `group_members` を SELECT できること」が前提になる。** `group_members` のRLS Policyが自分の所属グループに限定している場合、この問い合わせは0行を返し、**チェックが常に素通りする。**

本番DBで未確認のため、**判定は「案ア／ウ＋事前確認SQLの通過を条件とする」形でいただきたい。** SELECT が通らなければ案イ（新規RPC）に倒れる。

### 起案側の意見

**案ウ（案ア＋運用でカバー）を推す。** 第7-1章が既に「枠を奪われたら作り直す」と割り切っており、厳密な排他に見合うコストではない。ただし上記のRLS確認は必須とする。

## 5. 論点4【E6】写真投稿権限と第119回判定の整合

**仕様書 第10章**：event では写真投稿は管理者のみ。表示制御だけに頼らず `upload-image` でも確認する。

1-3 のとおり実装は可能である。**論点は判定の整合性にある。**

`upload-image` L189-190 のコメントに、**第119回判定で「画像投稿の is_creator 限定を撤回」した経緯**が明記されている。E6 はこれを **event に限って再導入する**形になる。

### 確認いただきたいこと

1. **第119回判定を通常グループで覆さないこと**を条件として明記してよいか（起案側の理解：第119回は通常グループに対する判定であり、event は対象外）
2. 処理側の実装方式は次のどちらか

| 案 | 内容 |
|---|---|
| **案カ** | `group_members` の select に `is_creator` を追加し、`group_sessions` から industry を引く追加クエリ1本を Step 4 に足す |
| 案キ | industry をフロントからリクエストに含めて渡す |

**案カを推す。** 案キはクライアントの自己申告になり、処理側制御の意味を失う。

なお `upload-image` は Edge Function のため **Deploy が必要**であり、自動反映されない。

## 6. 論点5【E7】一般参加者に既読をどこまで見せるか

**仕様書 第11-1章**：event では一般参加者に他社の既読・未読を見せない。ただし記述が「**自分の確認状態程度に留めるか、既読表示自体を非表示にする**」と両論併記のまま確定していない。

| 案 | 内容 |
|---|---|
| **案サ** | 既読表示を完全に非表示（一般参加者には既読数も未読者一覧も出さない） |
| 案シ | 「自分は既読」の状態だけ残し、他者の人数・顔ぶれは出さない |

**案サを推す。** 分母（受信者数）が見えると出展者の総数が推測でき、他社の存在を間接的に露出する。実装も分岐が単純で、返信側の既読表示（仕様書 21-6）にも同じ制御をそのまま適用できる。

**★既読集計ロジック（`item_receivers` / `read_receipts` / `receiver_count`）は変更しない。** フロントの表示制御のみ。

## 7. 論点6【E10】期限切れの「専用画面」は新設か文言差し替えか

**仕様書 第14章**：期限切れ event では「このイベントは終了しました」の専用画面を表示し、「新しいグループを作る」ボタンを置く。

1-5 のとおり、**現状の `restoreSession()` は既に `screen-start`（作成／参加画面）へ誘導し、`start-expiry-notice` を表示している。** 通常グループにも同じ処理が効いている。

| 案 | 内容 |
|---|---|
| **案タ** | 専用画面は新設せず、`start-expiry-notice` の文言を event のときだけ「このイベントは終了しました」に差し替える |
| 案チ | 第14章のとおり専用画面（screen）を新設する |

**案タを推す。** 遷移先（screen-start）も「新しいグループを作る」ボタンも既に存在しており、案チは画面を1枚増やすだけで得るものが無い。第0章の観点でも、既存の期限切れ経路に分岐を1つ足すほうが安全である。

**あわせて確認**：`loadMyGroups()` からの期限切れ event 除外（第14章）は、L4236-4239 の `group_sessions` select に `expires_at` と `industry` を追加すれば実現できる。**通常グループの一覧は現行どおり期限切れも表示し続ける**（挙動を変えない）。この理解でよいか。

## 9. 不可侵領域（実装指示書に必ず記載する）

```
【不可侵・変更禁止】
- group_sessions / group_members / messages（L3保護領域）の列・制約・既存データ
- 既存RPC2本の本体（create_group_with_creator / join_group_with_member）
- 既読集計ロジック・realReadMap・read_receipts・receiver_count・item_receivers
- 保護4関数（restoreSession / joinGroup / generateSignageToken / ensureCurrentUser）
  ※ E10 で restoreSession の期限切れ分岐に触れる場合は判定条件に従い最小差分とする
- signage.html の token認証・token復元・エラー分類・5分ポーリング・深夜3時リロード
- signage-fetch の token検証・エラー分類・補完取得
- 通常グループ（industry != 'event'）の全挙動
- DBアクセスを js/ 配下5ファイルに新設しないこと（index.html メインscriptに集約）
- 新規JSファイルを作成しないこと
```
